3. 코드 주안점
  * 아키텍처
     core, advice, services로 나누어 의존의 방향을 단방향으로 관리했습니다.
     (의존 관계 : advice -> services -> core)
  * 식별자
    식별자는 AUTO_INCREMENT 기반 Long Id 나 UUID가 아닌 ULID를 사용하였습니다.
    사용한 이유는 ULID의 경우 시간 기반 (Timestamp) 로 생성되는 앞자리가 이후 정렬이나 연관관계로 묶이는 다른 테이블들을 조회할 경우 성능적으로 유리하다고 생각하여 도입하게 되었습니다.

    특히, 연관관계로 묶이는 데이터들을 ManyToOne 같은 JPA 애노테이션을 사용하기보다는 composite primary key를 적극적으로 사용했습니다.
    그 이유는 우선 테이블 간 의존성이 느슨해져 다른 도메인을 가진 서비스에서 코드 설계가 쉬워지고, 이후 각 도메인을 개별 컴포넌트로 배포할 시에도 분리가 유리하다고 생각했습니다.
    또한 composite primary key로 관리하였을 때, primary key가 가진 cluster ip의 특성을 통해 유사한 값들을 조회할 시 성능적인 이점을 가진다는 부분도 생각했습니다.
    별도로 Id를 명시하지 않으면 MySQL의 경우 내부적으로 auto increment key를 만들어 사용하게 되는데, 이 경우 primary key가 가지고 있는 cluster ip의 조회 이점을 충분히 활용하지 못한다고 생각하여 이런 식으로 설계하게 되었습니다.
  * 트랜잭션 분할 처리
    푸시 알림 전송 시 푸시 알림을 보내는 주체가 일반 사용자라면 users 테이블에서 정보를 조회 후 network io를 거쳐 push 알림을 보내야하는데, 이런 알림 로직의 경우 저희 서비스 특성 상 사용자 관점에선 주요한 기능이지만,
    서비스를 개발하는 관점에서 핵심 코드에 영향을 주면 안되는 부가적인 코드이기 때문에, 이러한 코드가 주요 코드에 영향을 주면 안되는다는 생각이 들었습니다. 인증/인가의 경우도 마찬가지로 OAuthGateway를 통해서 network io가 발생하게 되는데,
    이때 메서드 통째로 Transactional 애노테이션을 달게 되면 코드 변경에 따라 커넥션을 쓰레드가 잡고 있는 상태로 불필요한 network io 등이 발생하여 전체 시스템 성능에도 영향을 미칠 수 있을거라 판단하여 적절한 트랜잭션 분할과 비동기 처리의 필요성을 느끼게 되었습니다.
    그러나 한 클래스에서 메서드를 나누면 self-invoking 문제로 인해 트랜잭션 적용이 정상적으로 되지 않고, 클래스를 나누기엔 코드 복잡도가 굉장히 많이 올라갈 것이라고 생각했습니다.
    그래서 PersistenceOperationGateway 와 AsyncAdvice 등의 제네릭을 사용하는 인터페이스를 만들고 명시적으로 트랜잭션 구획이나 비동기 실행되는 구획을 나누어 범용성 있게 트랜잭션이나 비동기 블록을 나눌 수 있도록 하는 방식을 도입했습니다.

    CacheAdvice의 경우도 마찬가지의 이유로 만들었고, 이에 더하여 CacheAdvice의 경우는 현재 Cacheable 애노테이션을 사용하고 있는데, 기존 SpEL이 컴파일타임에 에러를 감지하지 못하기 때문에 사용하는 사용자 입장에서 메서드 파라미터 이름이 변경되거나 하는 등
    여러가지 수정사항에 유연하게 대응하기 힘들고, 이후 RedisTemplate 도입 등 구현 방식 변경에도 코드가 대응하기 힘들다는 생각이 들어서 CacheAdvice를 통해 캐시 사용 자체를 추상화하고, 외부로부터 정의된 key를 일관되게 전달받도록 하여 인자명 불일치 등 Runtime 예외를
    예방하고 비즈니스 요구사항에 따라 구현 방식 변경에도 유연하게 대처할 수 있도록 했습니다.

  * 인증/인가
    - 역할 기반 접근 제어 : ADMIN, USER, PENDING,LEAVED의 4가지 권한을 구분하여 기능을 제어하였습니다.
    - 적절한 추상화를 통해 이후 다른 종류의 OAuth (구글이나 깃허브 등) 를 추가할 때도 기존 코드 변경 없이 코드를 추가하기만 하면 자동으로 등록되도록 설계를 하였습니다.
      OAuthGatewayRegistry에서 OAuthGateway를 구현하는 클래스를 관리하고 gateway의 경우 oauth 2.0 공통 부분을 추상화하여 로그인 시 플랫폼 정보를 입력하면 자동으로 해당 플랫폼에 맞는 Gateway를 찾아 해당 gateway에서 authenticate하는 방식으로 구현했습니다.
  * 친구
     - 친구 요청 관리 : 친구 요청을 보내고 수락/거절할 수 있는 기능 구현
     - 중복 방지 : 이미 친구 관계에 있거나 동일한 요청이 중복되는 것을 방지
     - 친구 목록 조회 : 친구 목록을 효율적으로 조회할 수 있는 최적화된 쿼리 설계
     - 푸시 알림 : 친구 신청이 오거나, 친구 신청이 수락된 경우 푸시 알림을 통한 확인 가능

     친구의 경우 from, to 칼럼을 두어 양방향으로 (from A to B, from B to A) 데이터가 존재할 경우만 A와 B의 친구 관계를 인식하는 방식으로 구현하였습니다.
     폐쇄형 서비스이기에 서로 친구 관계에 동의를 해야만 친구 추가가 되고, 음악 공유 등 주요 기능을 사용할 수 있도록 했는데, 단순히 id를 auto increment로 하여 관리하면 상술한 것 처럼 cluster ip의 장점을 활용하지 못하고, 기타 다른 방식을 사용하게 되면 칼럼 이름이 명시적이지      못하게 되거나 칼럼 용도가 모호해져서 다른 사람이 코드를 보았을 때 이해하기 힘들 것 같다는 생각하게 해당 방식으로 구현하게 되었습니다. 이 과정에서 적절한 join 조건을 통해 일정 부분 쿼리 튜닝 과정 또한 거쳤습니다. 
  * 음악 검색
     음악 검색 시 현재 spotify api를 이용하는데, 이때 client id와 secret을 통해 발급받은 키를 사용해야합니다.
     하지만 검색마다 access token을 새로 발급받는 것은 불필요한 기작이라고 생각하여 MusicPlatformAuthenticationManager를 통해 토큰을 캐싱하고 반환하도록 구현했습니다.
     또한 스케줄러를 통해 일정 시기마다 access token이 만료되기 전에 미리미리 갱신하도록 하여 Hot Key 만료 문제도 대응할 수 있도록 했습니다.
